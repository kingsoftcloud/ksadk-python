# 自定义请求数据透传方案（自研 UI + LangGraph Agent)

> 面向：用 LangGraph 编写 agent、并使用自研 UI（非托管 hosted UI）调用 ksadk server 的开发者。
> 目标：把"自定义请求头 / 自定义业务数据"从 UI 一路传到 agent 业务代码里可读。

---

## 1. 背景与结论

自研 UI 调 ksadk 的 `RunAgent` 接口时，常需要把一些 per-request 的业务数据（如 `user_id`、`trace_id`、租户、灰度标记、上游业务上下文）传给 agent，在 node / 工具里使用。

**核心结论：**

- 这类数据属于"请求级元数据"，**不要塞进 prompt / messages**，要走专门的透传通道。
- 因为 UI 是自研的，**优先用请求 body 里的 `Metadata` 字段传，而不是 HTTP header**。header 在走 agentengine 托管 gateway 时可能被中间层按白名单剥掉，body 不受影响。
- ksadk 已内置三条注入/读取通道。`RunAgent.Metadata` 已在本地 runtime 和 hosted server 链路落地，业务侧可直接读取。

---

## 2. 整体链路

```
自研 UI
  │  POST /agentengine/api/v1/RunAgent
  │  body: { AgentId, Messages, Metadata: { ...自定义... } }
  ▼
ksadk server (run_agent_action)
  │  把 Metadata 装进 PlatformInvocationContext / request_metadata
  ▼
LangGraphRunner
  │  ├─ 路径A: ksadk_prepare_state()  → 写进图的初始 state
  │  └─ 路径B: platform_invocation_scope() → ContextVar
  ▼
业务 node / 工具
     ├─ 路径A: 从 state 读
     └─ 路径B: from ksadk.runtime_context import get_current_invocation_context()
```

---

## 3. ksadk 现有的三条通道（先理解再选）

### 3.1 `ksadk_prepare_state(payload, session_context) -> dict`(LangGraph 专用）

定义在**你的 agent 模块**里，LangGraphRunner 在拼图初始 state 前调用。

- `payload`:server 归一化后的本次输入。
- `session_context`:`{session_id, history, is_resume, platform_context, kb_context, memory_context}`。
- 返回值：直接作为 LangGraph 的初始 `state`。

**适用：自定义数据需要进入图的 state schema（尤其自定义 State TypedDict 的图）。**

### 3.2 `ksadk_prepare_input`(LangChain 专用）

LangChainRunner 的同款 hook，把输入转成 runnable 的 input。LangGraph agent 用不到，了解即可。

### 3.3 `ksadk.runtime_context` —— 任意深度读取（ContextVar)

```python
from ksadk.runtime_context import (
    get_current_invocation_context,   # 取整个 PlatformInvocationContext
    get_current_user_id,              # 便捷取 user_id
    get_current_account_id,           # 便捷取 account_id
)
```

runner 跑每个 turn 时把 `PlatformInvocationContext` 写进 `ContextVar`，业务代码在**任意调用深度**（包括深层工具、回调）都能读，无需层层透传参数。

**适用：不想污染 state schema，只需要在代码里随时拿到请求级数据。**

`PlatformInvocationContext.metadata` 只包含调用方自定义字段；`agentengine` 是平台保留命名空间，不会作为用户 metadata 暴露。相同内容也会进入 `ksadk_prepare_state` 的 `session_context["platform_context"]["metadata"]`。

## 4. 推荐方案：RunAgent body 增加 `Metadata` 字段

### 4.1 UI 侧（自研，前端自己写，直接放 body)

```json
POST /agentengine/api/v1/RunAgent
Content-Type: application/json

{
  "AgentId": "my-agent",
  "Messages": [{ "role": "user", "content": "..." }],
  "SessionId": "sess-001",
  "Metadata": {
    "trace_id": "abc-123",
    "tenant": "acme",
    "gray_flag": "v2",
    "biz": "{\"order_id\":\"o-9\"}"
  }
}
```

Hosted server 的 `RunAgent.Metadata` 与 OpenAI Responses metadata 的公开边界一致：

- 最多 16 个用户键；
- key 最长 64 字符；
- value 必须是字符串，最长 512 字符；
- 复杂业务对象由调用方 JSON 编码为字符串；
- `agentengine` 由平台保留，调用方同名字段会被剥离并由平台值覆盖。

这些限制既控制请求体进入 runtime 后的内存开销，也避免 hosted `RunAgent` 通过内部 Responses 链路时改变 OpenAI 的 metadata 语义。

### 4.2 server 侧（已落地）

```python
# ksadk/server/app.py

class RunAgentActionRequest(BaseModel):
    ...
    Metadata: Optional[Dict[str, Any]] = None

# run_agent_action 内先剥离平台保留字段，再分别传入运行控制和业务 context
custom_metadata, runtime_controls = _split_custom_metadata(request.Metadata)
```

`PlatformInvocationContext.metadata` 已纳入 `to_payload()`。Responses、chat-completions 的流式与非流式、Background detached stream、resume 都使用同一 request scope；并发请求的 ContextVar 值彼此隔离，后台 task 在创建时继承自己的 context。

### 4.3 agent 业务侧读取（二选一或都用）

**路径 A —— 进图 state（用 `ksadk_prepare_state`):**

```python
# agent.py
def ksadk_prepare_state(payload: dict, session_context: dict) -> dict:
    platform = session_context.get("platform_context") or {}
    meta = platform.get("metadata") or {}
    return {
        "messages": ...,
        "trace_id": meta.get("trace_id", ""),
        "tenant": meta.get("tenant", ""),
    }
```

之后在任何 node 里通过 `state["trace_id"]` 使用。

**路径 B —— 任意深度读取（用 `runtime_context`):**

```python
from ksadk.runtime_context import get_current_invocation_context

def my_node(state, config):
    ctx = get_current_invocation_context()
    meta = (ctx.metadata if ctx else {}) or {}
    tenant = meta.get("tenant")
    ...
```

## 5. 为什么不用 HTTP header

| 对比项 | body `Metadata`（推荐） | HTTP header |
|---|---|---|
| 托管 gateway 透传 | ✅ 不受影响 | ⚠️ 默认按白名单转发，自定义 header 可能被剥掉 |
| 前端改造成本 | 低（UI 自研，直接加字段） | 低，但依赖中间层配置 |
| 类型表达 | OpenAI-compatible 字符串键值；复杂对象 JSON 编码 | 只能是字符串 |
| server 改动 | 加一个 body 字段 | 需注入 `Request` + 白名单解析 |

如果坚持走 header（例如对接某些只能改 header 的网关），需要：
1. server 入口签名注入 FastAPI `Request`，白名单方式挑 `X-*` header;
2. 确认 agentengine gateway / router 的 header 转发白名单已放行对应 header。
否则数据会在中间层丢失。**一般不推荐。**

---

## 6. 选型速查

| 诉求 | 用哪条 |
|---|---|
| 数据要进图 state、参与图内流转/持久化 | `ksadk_prepare_state` 写 state |
| 只想在 node/工具/回调任意深度读 | `runtime_context.get_current_invocation_context()` |
| LangChain agent（非 LangGraph) | `ksadk_prepare_input` |
| 自定义数据从哪进来 | RunAgent body `Metadata` 字段 |
